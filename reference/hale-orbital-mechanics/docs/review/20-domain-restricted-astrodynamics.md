# Domain Review: Three-Body Problem & Restricted Dynamics (`restricted-astrodynamics`)

**Reviewer:** Domain Analyst (L3), Phase 3 Deep Dive
**Scope:** `ada/src/threebody/hale_orbital-threebody.ads/.adb`, `python/three-body-extension/src/threebody/*`, its `tests/`
**Cross-domain touchpoints noted but not audited:** `ada/src/hale_orbital-types.ads` (dimensional-foundation), `ada/src/hale_orbital-matrices.ads` (dimensional-foundation), `ada/tests/run_tests.adb` / `run_all_tests.adb` / `hale_tests.gpr` (test infrastructure, not explicitly owned by any of the four numbered domains), `.github/workflows/ci.yml`.

---

## 1. Responsibility

This domain implements the Circular Restricted Three-Body Problem (CR3BP): given two massive "primary" bodies in circular orbit about their barycenter, it computes the equilibrium (Lagrange) points, propagates a massless third body's trajectory in the rotating frame, and analyzes the stability/periodicity of orbits (Halo, Lyapunov) around those equilibria. The Ada package (`Hale_Orbital.Threebody`) is the certified production implementation used by the library; the Python package (`threebody`, under `three-body-extension/`) is an independent "oracle" meant to cross-check the Ada math using a different numerical toolchain (SciPy/NumPy) rather than being consumed by any product code.

## 2. Key Modules

### Ada (`ada/src/threebody/`)
- `hale_orbital-threebody.ads` (391 lines) — public spec: `Threebody_System`/`Normalized_State` records (ads:26-42), predefined systems (ads:48-50, bodies at ads:361-380), Lagrange point API (ads:66-79), CR3BP equations (ads:86-111), `Propagate`/`Integration_Method` (ads:117-128), linear `Analyze_Stability` (ads:142-147), dimensional conversions (ads:154-179), STM types and `Propagate_With_STM` (ads:182-206), monodromy/Floquet types (ads:208-241), periodic-orbit finder API (ads:243-319), SPARK Ghost proof predicates (ads:322-356).
- `hale_orbital-threebody.adb` (1300 lines) — single monolithic body implementing all of the above (see Data Flow below for the most load-bearing routines).

### Python (`python/three-body-extension/src/threebody/`)
- `constants.py` — mass ratios and dimensional constants (SI/km/s) for 5 systems; `MU_CRITICAL_ROUTH` Routh stability threshold (constants.py:64).
- `cr3bp.py` — `pseudo_potential`, `pseudo_potential_derivatives`, `equations_of_motion`, `equations_of_motion_with_stm` (42-element augmented state, cr3bp.py:144-212), `jacobi_constant`, rotating/inertial frame transforms.
- `lagrange.py` — `lagrange_point_L1..L5` via `scipy.optimize.newton`/`brentq` (lagrange.py:24-157), `linearized_dynamics_at_lagrange` using full `np.linalg.eigvals` (lagrange.py:292-356), `classify_lagrange_point`.
- `integrators.py` — `rk4_step`, `rk45_step` (genuine embedded RKF4(5) with adaptive step, integrators.py:86-157), `propagate_fixed_step`/`propagate_adaptive` (wraps `scipy.integrate.solve_ivp`), event-detection helpers.
- `periodic.py` — Richardson halo initial guess (`richardson_halo_initial_guess`, periodic.py:55-120, explicitly "simplified", `Ax = Az` at periodic.py:107), Lyapunov initial guess (L1/L2 only — L3 raises `ValueError` at periodic.py:152), single-shooting differential correction (`differential_correction_planar`/`_3d`), `continue_family`.
- `stability.py` — `compute_monodromy_matrix`, `analyze_stability` (full `np.linalg.eig`, more rigorous than the Ada power-iteration approach — see Quality observations), invariant-manifold sampling/globalization, `find_heteroclinic_connection` (brute-force pairwise distance search, stability.py:390-403 — O(n²) over integrated trajectories, no bracketing/refinement).
- `systems.py` — `System` dataclass with dimensionalization helpers; 5 predefined systems (`SUN_EARTH`, `EARTH_MOON`, `SUN_JUPITER`, `SUN_MARS`, `SUN_VENUS`) vs. the Ada side's 3.
- `__init__.py` — public re-exports; **docstring example is broken**: `system.lagrange_points()[1]` (`__init__.py:21`) is called as a method on `System`, but `System` (systems.py:33-173) defines no `lagrange_points` method — the free function `lagrange.lagrange_points(mu)` is the real API. This is a doc/API mismatch, not exercised by any test.

## 3. Data Flow — Worked Example: Computing L1 and Propagating a Nearby State

**Ada path (primary implementation):**
1. Caller selects/builds a `Threebody_System` (e.g., `Earth_Moon_System`, ads:361-366) with `Mass_Ratio` precomputed and stored as a literal.
2. `Compute_Lagrange_Point (System, L1)` (adb:42-92) starts from the Hill-sphere guess `Gamma := (Mu/3)**(1/3)` and runs up to 100 Newton-Raphson iterations (`Max_Iterations`, adb:16) on the quintic `f(gamma)` for L1, converging when `|Delta_Val| < 1.0e-12` (`Tolerance`, adb:15). Result: normalized `(X, Y)` plus `Distance` in km via `System.Distance` (adb:171).
3. A `Normalized_State` near L1 can be propagated with `Propagate` (adb:250-343), a fixed-step integrator selectable as `Euler`, `RK4`, or `RK45` (ads:117) — **but `RK45` silently executes the identical classical 4-stage RK4 branch as `RK4`** (`when RK4 | RK45 =>`, adb:304); there is no adaptive step-size logic or embedded higher-order solution anywhere in the Ada propagator. This contract mismatch is invisible to the caller (no error, no degraded-accuracy warning).
4. `Jacobi_Constant` (adb:234-244) can be checked before/after propagation; SPARK Ghost predicate `Jacobi_Is_Conserved` (ads:330-336) expresses the invariant for proof but is not itself a runtime check.
5. For periodic-orbit work, `Find_Lyapunov_Orbit`/`Find_Halo_Orbit` (adb:799-952, adb:1078-1268) do single-shooting differential correction using `Propagate_With_STM` (adb:575-701, a 42-element combined RK4 integrator for state+STM) to build a 2×2 or 3×3 correction Jacobian from selected STM entries, with ad-hoc step-limiting (e.g., `if abs (DVY0) > 0.1 then ...`, adb:933-935) rather than a formally damped/line-searched Newton step.

**Python "oracle" path (independent, not wired to Ada):**
1. `lagrange_point_L1(mu)` (lagrange.py:24-74) solves an equivalent but *differently formulated* root equation (rational form in `r1, r2` rather than Ada's quintic-in-`gamma` polynomial) via `scipy.optimize.newton` with `brentq` fallback, `tol=1e-12`.
2. `equations_of_motion`/`jacobi_constant` (cr3bp.py) mirror the Ada physics; `propagate_adaptive` uses `scipy.integrate.solve_ivp(method='RK45')` — a genuine adaptive Dormand-Prince-family integrator, unlike the Ada `RK45` stub.
3. `find_lyapunov_orbit`/`find_halo_orbit` (periodic.py:280-474) perform their own independent single-shooting correction using `numpy.linalg.solve` on a 2×2/3×3 STM-derived Jacobian.

**No code path connects the two implementations.** I found no script, fixture, or CSV file anywhere in the repository that runs the Ada and Python implementations against the same inputs and diffs the outputs — see External Dependencies below. Cross-validation, as currently implemented, is two separately-authored, separately-tested implementations of the same physics that happen to agree on the underlying equations (verified by inspection) but have never been programmatically compared. This directly contradicts the domain description in `docs/review/00-inventory.md:511` ("Test Coverage: Cross-validation: Python oracle → CSV reference data → Ada tests"): **no CSV reference-data files exist anywhere in the repository** (`find ... -iname "*.csv"` returns only `remaining_issues.csv` and two certification tracking sheets, none CR3BP-related).

Minor duplication/missed-reuse note for the dimensional-foundation reviewer.
- No file I/O, no network, no OS interaction, no external processes.

**Python:**
- `numpy` (installed: 2.4.6; `requirements.txt` floor `>=1.20`), `scipy` (installed: 1.17.1; floor `>=2.7`... actually `>=1.7`), `pytest` (installed: 9.1.1; floor `>=7.0`) — all satisfied. The floors are far below what's installed; no pinned ceiling exists, so a future `numpy`/`scipy` major-version deprecation could silently break the oracle with no CI signal until it happens (no `numpy<3` or similar ceiling in `requirements.txt`).
- `scipy.optimize.newton/brentq/fsolve`, `scipy.integrate.solve_ivp` — used for root-finding and adaptive integration; contracts assumed: convergence via `RuntimeError` handling (lagrange.py:68-72 etc.) and `sol.success` flag checks (integrators.py:272-283).
- No network calls, no file I/O beyond `matplotlib`-based example plotting (optional dep, not imported by library code), no deserialization.

**Contract mismatch found (Ada internal, not just Ada-vs-Python):** the private constant `Sun_Earth_System` (ads:368-373) stores `Mass_Ratio => 3.003467E-6`, but the same record's `Mu1`/`Mu2` fields (`132712440018.0`, `398600.4418`) imply `Mu2/(Mu1+Mu2) ≈ 3.0034806e-6` — a **≈4.5 ppm relative inconsistency** between the two representations of the same physical ratio, verified numerically:
```
computed  = Mu2/(Mu1+Mu2)      = 3.003480642487067e-06
stored    = Mass_Ratio          = 3.003467e-06
Python's  = MU_SUN_EARTH         = 3.003480593e-06   (agrees with computed, not with Ada's stored value)
```
`To_Normalized`/`To_Dimensional`/`Normalized_Time_To_Seconds` (adb:414-454) compute mean motion `N := Sqrt((Mu1+Mu2)/L**3)` from `Mu1`+`Mu2`, independently of `Mass_Ratio`, which is used everywhere else (Lagrange points, EOM, Jacobi constant, STM). For `Sun_Earth_System` these two paths are silently inconsistent with each other by ~4.5 ppm — small, but it is exactly the kind of undocumented cross-field invariant that DO-178C traceability is supposed to catch, and no precondition or Ghost function checks `Mass_Ratio = Mu2/(Mu1+Mu2)` anywhere in the package. (Earth-Moon and Sun-Jupiter constants are self-consistent to <2e-5 relative, i.e., within expected rounding of the underlying GM values.)

## 5. Invariants and Conventions

- **Normalization convention** (documented in `python/three-body-extension/specs/01-cr3bp-equations.md:1-15` and matched by the Ada implementation): length unit = primary separation, mass unit = `m1+m2`, time unit chosen so `G(m1+m2)=1` and orbital period `=2π`. Primary 1 (larger) sits at `x=-μ`, primary 2 (smaller) at `x=1-μ`, matching both `R1`/`R2` helpers (adb:23-36) and `cr3bp.py:57-58`.
- **Mass-ratio convention**: `μ = m2/(m1+m2)`, `m2` always the *smaller* body, `0 < μ < 0.5` enforced by nearly every Ada precondition (e.g. ads:70,78,146). Python does not enforce this via type contracts; it's convention-only, checked implicitly by callers.
- **Newton-Raphson exit conditions for L1/L2/L3** rely on `abs(FP) < 1.0e-15` to bail on a flat derivative (adb:79-81, 111-113, 144-146) — if this fires, the loop silently exits with whatever `Gamma` it had, with no `Converged`/`Success` flag returned by `Compute_Lagrange_Point`. Callers cannot distinguish a converged result from a stalled one; there is no error contract at all for this function (it's a pure function that must always return a `Lagrange_Result`, by construction).
- **State ordering** is fixed as `[x,y,z,vx,vy,vz]` (Ada `State_Array`, adb:262-273; Python state arrays, cr3bp.py:131,171) and, for STM propagation, `[state(6), Phi(36) row-major]` = 42 elements (Ada `Combined_State`, adb:582; Python `state[6:].reshape((6,6))`, cr3bp.py:174) — the two implementations agree on this layout, which is good, but it is an implicit convention with no shared schema/type definition enforcing it across languages.
- **Symplectic structure** is assumed but only loosely checked: Ada's own test suite validates `Phi^T J Phi ≈ J` to a "relaxed tolerance" of `0.01` (`hale_tests-periodic_orbits.adb:140`, outside my assigned directories but directly testing this domain's STM code) and Floquet reciprocal pairs to tolerance `0.5` (`hale_tests-periodic_orbits.adb:224`) — tolerances loose enough that a moderately buggy Jacobian would still pass.
- **Differential correction step-limiting** is done via ad-hoc clamps (e.g. `if abs (DX0) > 0.01 then DX0 := 0.01 * (DX0/abs(DX0))`, adb:1238-1239) rather than a principled line-search/trust-region method; convergence is not guaranteed and `Max_Iterations` (default 50) can be exhausted with `Converged = False` silently returned as a normal (non-exceptional) result — callers must check `.Converged`, and at least one Ada test (`Test_Halo_Periodicity`, `hale_tests-periodic_orbits.adb:371-385`) explicitly treats a non-converged orbit as still "passing" as long as `Period > 0.0`.

## 6. MATRIX FLAGS

### Security observations

- **No network, filesystem, deserialization, or auth surface in this domain** — it is pure numerical computation. This significantly limits classic security risk.
- **Input validation is precondition-only and is compiled out in release builds.** Ada preconditions like `Pre => Mu > 0.0 and Mu < 1.0` (e.g. ads:90, 101, 110) are the *only* guard against a degenerate mass ratio (which would cause division-by-zero/NaN in `R1`/`R2`, adb:23-36, or negative-under-sqrt in `Pseudo_Potential`). Per `docs/review/00-inventory.md:182`, the `release` build mode has "checks suppressed" — meaning in a release-mode certified build, an out-of-contract `Mu` (e.g. from a caller-constructed `Threebody_System` with a typo'd mass ratio) would not raise `Assertion_Error`; it would silently propagate NaN/Infinity through `Compute_Lagrange_Point`, `Propagate`, `Analyze_Floquet`, etc. This is a defense-in-depth gap for a DO-178C-track library where release-mode behavior on malformed input has no documented fallback.
- **`Analyze_Floquet` has no NaN/Inf guard** (adb:719-793) before computing `Is_Stable` from `Max_Multiplier`; if a prior propagation blew up (e.g., near-singular trajectory passing very close to a primary, `Is_Valid_State` Ghost predicate at ads:340-348 would catch this *in proof*, but there is no runtime call to it inside `Propagate`), a garbage monodromy matrix could produce a `Floquet_Result` that looks superficially valid (`Is_Stable` is a `Boolean`, not tagged with a validity flag).
- **Python oracle has no exposed attack surface** (no CLI reading untrusted files, no pickle/yaml/eval, no subprocess). `scipy.optimize.newton`/`fsolve` on attacker-influenced `mu` could hang or raise, but these are only called with internally-sourced `mu` values in the current codebase — not user/network input.
- **Test-only path manipulation**: every Python test and example file does `sys.path.insert(0, os.path.join(os.path.dirname(__file__), '..', 'src'))` (e.g. `tests/conftest.py:17`, `tests/test_cr3bp.py:10`) instead of an installable package (`pyproject.toml`/`setup.py` — neither exists per `docs/review/00-inventory.md:155`). Not itself a vulnerability, but it means there is no reproducible, pinned installation contract; whichever `threebody` module is first on `sys.path` at runtime wins, which is fragile if this package is ever vendored elsewhere.

### Quality observations

- **`Integration_Method.RK45` is a no-op alias for `RK4`, not an adaptive integrator.** `Propagate` (adb:250-343) has `when RK4 | RK45 =>` (adb:304) executing the identical fixed-step, 4-stage classical Runge-Kutta code for both enum values. The type name and public API (ads:117,125) strongly imply an embedded/adaptive Runge-Kutta-Fehlberg method (matching the Python oracle's genuine `rk45_step`, `integrators.py:86-157), but none exists. Any Ada caller who selects `RK45` expecting adaptive accuracy silently gets fixed-step `RK4` at whatever `Step_Size` they passed (default `0.001`). This is the most significant functional gap I found in the domain.
- **`Analyze_Floquet` only computes 2 of 6 Floquet multipliers correctly.** The function initializes `Result.Multipliers(I)` to the raw diagonal entries of the monodromy matrix for all `I in 1..6` (adb:740-742) — which are *not* eigenvalues for a general (non-diagonal) matrix — then overwrites only `Multipliers(1)` (dominant eigenvalue via power iteration) and `Multipliers(2)` (its reciprocal, assumed via the symplectic property, adb:779-784). `Multipliers(3..6)` remain mathematically meaningless diagonal entries. This is self-documented as a known simplification ("Full eigenvalue computation requires QR iteration - simplified here", adb:735-736) but the returned `Floquet_Result.Multipliers` array gives no indication to callers that 4 of its 6 entries are not real eigenvalues. `Max_Multiplier`/`Is_Stable` (the fields actually used by the one Ada stability test, `hale_tests-periodic_orbits.adb:205`) are computed correctly via power iteration, so the primary stability verdict is likely sound, but any consumer using `Multipliers(3..6)` (e.g., for resonance or bifurcation analysis) would get wrong answers with no warning. The Python oracle's `analyze_stability` (stability.py:97-159) does a full `np.linalg.eig` and is strictly more correct here — but nothing cross-checks the two.
- **The 20+ periodic-orbit Ada tests are not wired into the CI-executed test binary.** `hale_tests-periodic_orbits.adb`/`.ads` (STM identity/propagation/symplectic checks, monodromy, Floquet, Lyapunov L1/L2, Richardson guess, Halo L1/L2, orbit-family generation, Jacobi conservation — `hale_tests-periodic_orbits.adb:1-501`) is only invoked from `Run_All_Periodic_Orbit_Tests` inside `ada/tests/run_all_tests.adb:21,375`. No `.gpr` project file anywhere in the repository (`hale_tests.gpr`, `hale_orbital.gpr`, `hale_examples.gpr`, `coverage.gpr`) lists `run_all_tests.adb` as a `Main`; only `run_tests.adb` is built (`ada/tests/hale_tests.gpr:11`), and CI only runs `./ada/bin/run_tests` (`.github/workflows/ci.yml:44-47`). `run_tests.adb`'s own `Test_Threebody` procedure (`run_tests.adb:503-549`) covers just 9 basic assertions (Lagrange point coordinates, L4/L5 stability, one Jacobi-constant sign check) — none of the STM/monodromy/Floquet/Halo/Lyapunov machinery is exercised by anything CI or the documented `./ada/tests/run_tests` build path actually runs. `remaining_issues.csv:35` (ISS-034) cites `hale_tests-periodic_orbits.ads/adb with 20+ tests` as evidence of "COMPLETED" status, but as currently wired those tests are dead code from a build/execution standpoint — this is a traceability gap material to the project's stated DO-178C ambitions (docs/certification/*, RTM). I recommend flagging this for the certification-safety and quality-audit reviewers explicitly, since it affects test-count claims made in `remaining_issues.csv` and possibly the RTM.
- **Python oracle has zero tests for `periodic.py` and `stability.py`.** `tests/` contains only `test_cr3bp.py`, `test_integrators.py`, `test_lagrange.py`, `conftest.py` — confirmed by directory listing; no `test_periodic.py`/`test_stability.py` exist. I ran the full suite read-only: `python3 -m pytest -x --tb=short -q` under `python/three-body-extension` → **49 passed, 0 failed** (numpy 2.4.6, scipy 1.17.1, pytest 9.1.1, all above the `requirements.txt` floors). This matches the inventory's claim that "periodic and manifold modules [are] partial" (`docs/review/00-inventory.md:398-400`) — but concretely, it's not partial *implementation*, it's **zero automated test coverage** for two fully-implemented, non-trivial modules (differential correction, monodromy/manifold computation, heteroclinic search). A smoke run I did manually (`find_lyapunov_orbit(EARTH_MOON.mu, 0.01, L_point=2)`) succeeded and converged, but took **~75 seconds** for one small-amplitude orbit — `differential_correction_planar` re-propagates the full trajectory from `t=0` every Newton iteration with `dt=0.0001` fixed steps (`periodic.py:202-204`) rather than reusing intermediate results or using a coarser/adaptive step, which is a latent performance hotspot if this module is ever used interactively or in a continuation loop (`continue_family`, `periodic.py:477-537`, would multiply this cost by `n_orbits`).
- **`periodic.py` Richardson halo guess is admittedly oversimplified** (`Ax = Az  # Simplified; actual relation is more complex`, periodic.py:107) compared to the Ada `Richardson_Halo_Guess` (adb:954-1076), which implements the fuller third-order Richardson amplitude-constraint algebra (`A21`, `A22`, `A31`, `L1_Coef`/`L2_Coef`, adb:1023-1042). The Python initial guess is thus weaker than Ada's, and Python's `find_lyapunov_orbit` doesn't support L3 at all (`raise ValueError("L3 Lyapunov not yet implemented")`, periodic.py:152), while Ada's `Find_Lyapunov_Orbit` explicitly allows `Point in L1 | L2 | L3` (ads:273). This is a concrete, citable oracle-coverage gap: **Ada's L3 Lyapunov-orbit path has no Python cross-check available even in principle**, on top of the general lack of any actual cross-validation harness (see Data Flow).
- **`SUN_MARS`/`SUN_VENUS` systems exist in the Python oracle** (`systems.py:201-213`) **with no Ada counterpart** (`Threebody_System` only predefines Earth-Moon, Sun-Earth, Sun-Jupiter, ads:48-50,361-380). Minor scope asymmetry between "oracle" and "implementation," worth tracking if oracle parity is a stated goal.
- **`docs/rationale/DEC-005-threebody-package-structure.md` is stale.** It states the package is "~686 lines" (line 20) and that "Periodic" orbit search is a "deferred feature… not yet implemented" (lines 91-98, referencing ISS-034 as open), and frames future splitting "when ISS-034 (periodic orbits) is implemented" (line 187) — but ISS-034 is marked `COMPLETED` in `remaining_issues.csv:35` and the actual `.adb` is 1300 lines (nearly double), with STM/monodromy/Floquet/Lyapunov/Halo/Richardson/family-generation all present. This decision record should be revisited per its own stated trigger condition but apparently has not been.
- **`__init__.py` docstring example is broken** (see Key Modules) — `system.lagrange_points()[1]` doesn't exist on the `System` dataclass. Low-severity (docs only, not doctested), but indicates the package-level example was never executed/CI-checked (no `--doctest-modules` in the pytest config I could find).
- **No dead-code concerns found in the Ada `.adb`** beyond the above — the file is dense but each function is reachable from the public spec.
