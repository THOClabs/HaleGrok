## 1. Responsibility

This domain is the mathematical bedrock of the library: it defines the numeric representation (`Real`, a 64-bit float), the dimensioned scalar subtypes (distance, velocity, time, angle, mass, gravitational parameter, specific energy/momentum), the physical/mathematical constants (solar-system bodies, math constants, numerical thresholds), and the 3D vector/matrix algebra that every other Ada package builds on. Nothing in `ada/src` performs orbital mechanics without first going through these types, constants, and linear-algebra primitives — 22 of the 24 other `.ads`/`.adb` files in `ada/src` `with` one or more of `Hale_Orbital.Types`, `.Constants`, `.Vectors`, or `.Matrices` (verified by grep; see §4).

## 3. Data flow

Representative operation — a caller in another domain (e.g. `Hale_Orbital.Twobody.Specific_Energy`, `ada/src/hale_orbital-twobody.ads:27-33`) computing orbital energy from a state vector:

1. **Entry**: caller supplies `R : Position_Vector`, `V : Velocity_Vector` (both are `Vector_3D` of raw `Real` components — see §5 caveat) and `Mu : Gravitational_Parameter` (a distinct dimensional type from `hale_orbital-types.ads:50`).
2. **Precondition evaluation**: the callee's contract calls `Vectors.Magnitude_Squared (R) > 0.0` (`hale_orbital-vectors.ads:68-70`) and `Real (Mu) > 0.0` — note the explicit `Real(...)` cast required because `Gravitational_Parameter` is a distinct derived type and cannot be compared to a literal without conversion.
3. **Vector algebra**: internal computation uses `Vectors.Dot`/`Vectors.Magnitude` (`hale_orbital-vectors.adb:53-77`) operating purely on `Vector_3D`/`Real`; no dimensional-type information survives into vector math.
4. **Constants** are pulled in via `with Hale_Orbital.Constants; use ...` where a caller needs `Pi`, `Mu_Earth`, etc. (e.g. `hale_orbital-constants.ads:29,69`).
5. **Exit**: result is converted back to a dimensional type at the function boundary, e.g. `return Hale_Orbital.Types.Specific_Energy(...)`, and exceptions (`Physical_Error`, `Singularity_Error`) propagate out of `Vectors`/`Matrices` (`hale_orbital-vectors.adb:83,114,133`; `hale_orbital-matrices.adb:129,193`) for callers to handle or let escalate to `Convergence_Error`/`Invalid_Orbit` at higher levels.

In short: dimensional types provide a typed "shell" at package boundaries; all actual arithmetic happens in the undimensioned `Real`/`Vector_3D`/`Matrix_3x3` representations, with the shell re-applied via explicit conversions on the way out.

## 5. Invariants and conventions

- **Dimensional distinctness is scalar-only.** Because each dimensional subtype is declared `new Real` (e.g. `Distance_Km`, `Velocity_Km_S` — `hale_orbital-types.ads:35,38`), Ada treats them as distinct derived types: direct arithmetic mixing two different dimensional types (e.g. `Distance_Km + Time_Seconds`) is a compile error, which is a genuine and useful safety property. However, by ordinary Ada derived-type semantics, each type also inherits its own self-typed operators (`Distance_Km * Distance_Km -> Distance_Km`), so the compiler does **not** perform true dimensional analysis — a formula that squares a distance still type-checks as `Distance_Km`, not a hypothetical "km²" type. The safety net catches *swapped-argument*/*wrong-quantity-kind* bugs, not *dimensionally-incorrect formulas* that stay within one quantity kind.
- **Vector/matrix types carry no dimensional information at all.** `Position_Vector` and `Velocity_Vector` (`hale_orbital-types.ads:66,69`) are Ada `subtype`s of the same `Vector_3D`, not distinct derived types, so they are statically interchangeable — a `Velocity_Vector` can be silently passed where a `Position_Vector` is expected with no compiler diagnostic. `Vectors`/`Matrices` operate purely on `Vector_3D`/`Matrix_3x3`/`Real`; dimensional typing exists only at the outer function-signature level (e.g. `Twobody.Specific_Energy(R : Position_Vector; V : Velocity_Vector; ...)`), not within the linear-algebra library itself. This materially narrows the "compile-time unit safety" claim in the file header comments (`hale_orbital-types.ads:5`).
- **Explicit `Real(...)` conversion convention.** Contracts throughout the domain and its consumers convert dimensional types to `Real` before comparison/arithmetic (e.g. `hale_orbital-twobody.ads:32,40-41,73-75`). This is a consistent, intentional pattern — any new function added to this layer should follow it.
- **Numerical threshold duplication.** `Small_Threshold : constant Real := 1.0e-15` is defined once (`hale_orbital-types.ads:135`) and is correctly reused by `twobody.ads:40,74,184,194` and `lambert.adb:45`, but `Vectors` and `Matrices` bodies hardcode the same `1.0e-15` literal directly instead of referencing the named constant: `hale_orbital-vectors.adb:82,113,132,193,208,219` and `hale_orbital-matrices.adb:128,192`. This is a DRY/traceability gap, not just style: `docs/rationale/DEC-009-numerical-thresholds.md` is the project's DO-178C threshold-justification record and explicitly enumerates file/line locations using the `1.0e-15` division-safety threshold (`twobody.adb:164/177`, `kepler.adb:51`, `elements.adb:447`) but **does not list any location in `vectors.adb` or `matrices.adb`**, even though both files use the identical literal for the identical purpose (guarding division/normalization/inversion). The certification rationale document is therefore incomplete for this domain.
- **`Pi` is duplicated as a raw literal rather than imported.** `Vectors` does not `with Hale_Orbital.Constants` (only `with Hale_Orbital.Types` — `hale_orbital-vectors.ads:10`), so the postcondition on `Angle_Between` hardcodes `3.14159265358979` (`hale_orbital-vectors.ads:99`) instead of referencing `Constants.Pi` (`hale_orbital-constants.ads:29`, which carries more digits: `3.14159_26535_89793_23846`). Both round to the same double-precision value in practice, but this is a second instance of the same avoidable-duplication pattern.
- **Error contract**: this domain signals failure via Ada exceptions, not return codes/booleans — `Physical_Error` (zero-vector normalize/project/angle, zero rotation axis) and `Singularity_Error` (singular-matrix inversion) are raised directly from `Vectors`/`Matrices` bodies (`hale_orbital-vectors.adb:83,114,133`; `hale_orbital-matrices.adb:129,193`), consistent with the exception set declared once in `hale_orbital-types.ads:191-200` and reused library-wide.
- **`pragma Pure`** is applied to `Hale_Orbital`, `.Types`, `.Constants`, `.Vectors`, `.Matrices` (`hale_orbital.ads:30`, `types.ads:15`, `constants.ads:23`, `vectors.ads:16`, `matrices.ads:16`), meaning no package state and no side effects are permitted — an appropriate and consistently-applied invariant for a foundational math layer, reinforced by `Global => null` on effectively every subprogram contract in `Vectors`/`Matrices`.
- **Tolerance inconsistency inside `Matrices`.** `Is_Singular` defaults to flagging a matrix as singular when `abs(Determinant) < 1.0e-12` (`hale_orbital-matrices.ads:69`, body at `matrices.adb:118-121`), but `Inverse` only raises `Singularity_Error` when `abs(Det) < 1.0e-15` (`matrices.adb:128-130`) — three orders of magnitude looser. A matrix with determinant between `1e-15` and `1e-12` is reported "singular" by `Is_Singular` yet will be silently (successfully) inverted by `Inverse`, producing a numerically unstable result without any diagnostic. Any caller relying on `Is_Singular` as a pre-check before calling `Inverse` gets a false sense of safety at that boundary.

## 6. MATRIX FLAGS

### Security observations

- **No auth, network, secrets, or deserialization surface** in this domain — it is pure arithmetic over in-memory floating-point data. No filesystem or environment access either (see §4). This significantly limits the traditional "security" attack surface; the residual risk class is purely numerical/logic robustness (see below), which matters here mainly because this is a DO-178C-aspirational safety-critical library.
- **Documentation/verification-claim mismatch (most notable finding in this domain).** `hale_orbital-vectors.ads:7` states "SPARK Status: This package is proven free of runtime errors," and `hale_orbital-matrices.ads:7` states "SPARK Status: Pure matrix operations, formally verifiable." However, the corresponding bodies explicitly disable SPARK analysis: `hale_orbital-vectors.adb:8` — `with SPARK_Mode => Off  --  Body uses generic instantiation`, and `hale_orbital-matrices.adb:8` — same. With `SPARK_Mode => Off`, `gnatprove` does not analyze the body at all (not even flow analysis), so the specific claim "proven free of runtime errors" cannot be substantiated by the code as structured — the exception-raising logic (`raise Physical_Error`, `raise Singularity_Error`), the division operations, and the array-index math inside these two bodies are outside SPARK's reach. The same pattern applies to the root package (`hale_orbital.ads:27` `SPARK_Mode => On` vs. `hale_orbital.adb:6` `SPARK_Mode => Off`), though the stakes there are lower (a version-string formatter). Given this is a certification-aware repository (`docs/certification/`), this spec-vs-body proof-scope gap is worth flagging to the certification-safety domain reviewer as a documentation-accuracy issue at minimum, and a false-assurance risk at worst.
- **Untrusted-input parsing**: none of these files parse external/untrusted input (no string parsing of orbital elements, no config file reads). `Real(...)` conversions from caller-supplied dimensional values are the closest thing to "input handling," and they rely entirely on Ada's compile-time type system plus runtime `Pre`/`Post` contracts — contracts that are only enforced when compiled with assertions/contract-checking enabled (debug/spark build modes per `ada/hale_orbital.gpr`, per inventory §4.1) and are compiled out in `release` mode's "checks suppressed" configuration (per inventory §4.1). That means in a release build, malformed dimensional inputs (e.g., negative distance, zero denominator not otherwise guarded) could silently produce NaN/Inf or a Constraint_Error-free garbage result rather than a controlled exception, since the `Pre`/`Post` aspects are the only place those invariants are checked. This is a build-mode-dependent robustness gap worth flagging to the quality/certification reviewers, not a classic security vulnerability.

This is either dead code or a missed reuse opportunity for the classical-astrodynamics domain reviewer to weigh in on.
  - `Vectors.Rotate_X`, `Rotate_Y`, `Rotate_About_Axis`, `Cartesian_To_Spherical`, `Spherical_To_Cartesian`, `Are_Parallel`, `Are_Perpendicular`, `Angle_Between`, `Perpendicular_Component`, `Is_Zero` similarly have **zero call sites anywhere else in `ada/src`** (grep confirmed). Only `Vectors."+"`, `"-"`, `Dot`, `Cross`, `Magnitude`, `Magnitude_Squared`, `Normalize`, `"*"`, `"/"` appear to be exercised by other domains.
  - The six SPARK Ghost lemma functions (`Is_Valid_Magnitude`, `Is_Unit_Vector`, `Are_Orthogonal`, `Cross_Product_Is_Orthogonal`, `Dot_Is_Commutative`, `Rotation_Preserves_Magnitude` — `hale_orbital-vectors.ads:161-196`) are declared but never referenced in any `Pre`/`Post`/`pragma Assert` anywhere in the codebase (grep confirms matches only within their own declaration file). They currently function as unused self-documentation rather than proof-carrying artifacts.
- **Test coverage gaps.** `ada/tests/run_tests.adb:54-121` (`Test_Vectors`, `Test_Matrices`) is the only direct test coverage found for this domain: 5 assertions for `Vectors` (`"+"`, `Dot`, `Cross`, `Magnitude`, `Normalize`) and 3 for `Matrices` (identity multiply, `Determinant`, one `Rotation_Z` case). `ada/tests/hale_tests-edge_cases.adb:453-487` adds a handful more (`Rotation_X(0)`/`Rotation_Y(0)` = identity, `Transpose` of identity). Everything flagged as unused above is also, unsurprisingly, untested: no test exercises `Inverse`, `Is_Singular`, `Rotation_Axis_Angle`, `Perifocal_To_Inertial`/`Inertial_To_Perifocal`, `Rotate_X/Y`, `Rotate_About_Axis`, `Cartesian_To_Spherical`/`Spherical_To_Cartesian`, `Are_Parallel`, `Are_Perpendicular`, `Angle_Between`, `Perpendicular_Component`, `Is_Zero`, `Trace`, `Matrix_6x6` arithmetic (`"+"`, `"*"`, `Transpose`), or the exception paths (`Physical_Error` on zero-vector `Normalize`/`Project`/`Angle_Between`/`Rotation_Axis_Angle`; `Singularity_Error` on `Inverse`). For a foundational, `pragma Pure`, widely-depended-upon layer in a DO-178C-aspirational project, this is a materially thin test-coverage footprint relative to its blast radius.
- **Tolerance/threshold inconsistency**: see §5 — `Is_Singular` (1e-12) vs. `Inverse`'s internal check (1e-15) in `hale_orbital-matrices.ads:69` / `matrices.adb:118-121,128`. This is a latent correctness bug class (silent numerically-unstable inverse) more than a pure quality nit.
- **Certification traceability gap**: see §5 — `docs/rationale/DEC-009-numerical-thresholds.md` documents the `1.0e-15` and `1.0e-10`/`1.0e-12` thresholds used elsewhere but omits `Vectors`/`Matrices` usages entirely, which is a real gap for a project pursuing DO-178C-style numerical-constant traceability (see `docs/certification/`).
- **No complexity hotspots** in this domain — all functions are short (largest is `Matrices.Inverse` at ~25 lines, `hale_orbital-matrices.adb:123-148`), closed-form, and loop-free except the straightforward triple-nested-loop matrix multiplications (`hale_orbital-matrices.adb:67-78,257-268`), which are `O(n^3)` on fixed small `n` (3 or 6) and not a performance concern.
- **Minor style-only duplication**: `Pi` literal duplicated in `Vectors` postcondition instead of importing `Constants.Pi` (see §5) — low risk given both round to the same double value, but worth cleaning up for maintainability.
